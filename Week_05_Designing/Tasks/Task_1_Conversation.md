## Modular monolith for RecipeCove

A modular monolith would be **one web application deployed as one unit**, but internally divided into clear modules.

The application would not be a collection of completely separate services. Instead, all modules would run in the same process and communicate through well-defined internal interfaces.

A possible structure would be:

```text
RecipeCove application
│
├── Identity and Accounts
├── Recipe Catalog
├── Recipe Search
├── Favorites
├── Calendar
├── Chatbot and Recommendations
└── External Integrations
    ├── Google authentication
    └── AI chatbot provider
```

This approach fits the current scope described in [RecipeCove.txt](C:/Users/jahon/Documents/study/mAIN2_1/SWEwAI/AI4SE_Labs_2026/Week_05_Designing/Tasks/data/RecipeCove.txt).

## 1. Possible module responsibilities

### Identity and Accounts module

This module would handle:

- Registering users through Google.
- Logging users in and out.
- Managing sessions.
- Loading the current user.
- Storing basic profile information.
- Controlling access to registered-user functionality.

Other modules should not implement their own login logic. They should ask the Identity module questions such as:

```text
Which user is currently logged in?
Is this user allowed to perform this operation?
```

### Recipe Catalog module

This module would own recipe and ingredient information.

It would handle:

- Loading recipe details.
- Loading ingredient details.
- Checking whether a recipe exists.
- Managing recipe categories and diet labels.
- Possibly importing or updating recipe data.

The Favorites and Calendar modules might store a recipe identifier, but they should not directly manipulate recipe data.

This module would handle:

- Searching recipes by name.
- Filtering recipes by diet or other attributes if added later.
- Sorting and pagination.
- Returning matching recipes to the user interface.

Initially, this could use ordinary database queries. If search requirements later become more advanced, this module could be changed to use a search engine without changing the rest of the application.

### Favorites module

This module would handle:

- Adding a recipe to a user’s favorites.
- Removing a recipe from favorites.
- Listing a user’s favorite recipes.

### Calendar module

This module would handle:

- Creating calendars.
- Deleting calendars.

The exact fields would depend on requirements that are still missing.

This module would handle:

- Receiving a user’s diet request.
- Determining which recipes fit the request.
- Calling an external AI service, if one is used.
- Returning recipe suggestions.

The rest of the application should communicate with this module instead of calling an AI provider directly.

This could contain adapters for external services, such as:

- Google authentication.

- Email or notification services in the future.

## 2. How the modules would communicate

There are two useful communication styles inside the monolith.

### Direct application-service calls

For operations that need an immediate answer, one module can call another module’s public service.

For example:

```text
Search module
    → Recipe Catalog module
        → returns matching recipes
```

Or:

```text
Favorites module
    → Recipe Catalog module
        → verifies that recipe 123 exists
```

These calls would be ordinary in-process method or service calls. They would not involve network requests.

### Internal events

For actions that notify another part of the system, the application could publish an internal event.

For example:

```text
FavoriteAdded event
    → activity logging
    → recommendation history
    → optional notification
```

An internal event is useful when the original operation should not know every consumer that may be added later.

However, internal events should be introduced carefully. For a small system, ordinary service calls are easier to understand. Events are most useful for optional or independent follow-up work.

### Boundary rules

To keep the monolith modular:

- Each module should have its own application services.
- Each module should own its own business rules.
- Other modules should use public interfaces rather than internal classes.
- Modules should avoid directly changing another module’s tables.
- Shared code should be limited to genuinely common concerns such as identity types, errors, or date handling.
- Business logic should not be placed entirely in controllers or user-interface code.

The main risk is creating a “fake modular monolith” where every module directly accesses every other module’s classes and database tables.

## 3. One database or several?

### Recommended starting point: one relational database

For the current size of RecipeCove, I would start with **one relational database**.

The database could contain tables such as:

```text
users
recipes
ingredients
recipe_ingredients
favorites
calendars
calendar_events
diet_categories
```

However, one database does not mean that every module can freely access every table.

A better organization would be:

```text
Identity module:
    users

Recipe module:
    recipes
    ingredients
    recipe_ingredients

Favorites module:
    favorites

Calendar module:
    calendars
    calendar_events
```

Each module owns its tables. Other modules request information through the owning module’s interface.

### Why one database is suitable initially

One database provides:

- Simple deployment.
- Simple local development.
- Easier backups.
- Easier database migrations.
- Strong transactions.
- Lower operational cost.
- Simple queries for related recipe information.

For example, adding a favorite can be completed in a normal database transaction.

### When multiple databases might become useful

Separate databases could be considered later if:

- The system becomes very large.
- Modules need independent scaling.
- Different teams own different modules.
- The chatbot requires a separate data-processing system.
- Search needs a specialized search index.
- Independent deployment becomes important.
- A module has substantially different data-storage requirements.

Using several databases immediately would add complexity:

- More deployment and monitoring work.
- More complicated backups.
- No simple cross-database transactions.
- More difficult local development.
- More complex data synchronization.
- Possible stale or inconsistent data.

Therefore, the recommended trade-off is:

> Use one relational database now, but maintain module ownership so that parts can be separated later if necessary.

## 4. Advantages of the modular-monolith approach

### Simpler deployment

There is one application to build, configure, deploy, monitor, and back up.

### Lower operational complexity

The project does not immediately need:

- Service discovery.
- Multiple deployment pipelines.
- Distributed tracing.
- Message brokers.
- Network communication between every module.
- Complex container orchestration.

### Easier development

Developers can run the complete system locally without starting many independent services.

### Fast communication

Calls between modules happen inside the same application, so they do not have network latency.

### Easier transactions

For example, updating a favorite and creating related application data can use ordinary database transactions.

### Easier debugging

A request can be followed through one application and one set of logs.

### Good fit for current scope

RecipeCove appears to have a moderate number of features and user roles. It does not currently have clear requirements for extremely high traffic or independent team ownership.

### Future flexibility

If the module boundaries are respected, a module such as Search or Chatbot can later be extracted into a separate service.

## 5. Disadvantages and risks

### Modules share one deployment

A problem in one module can affect the whole application.

For example, a serious defect in chatbot handling could consume too many resources and affect recipe searches.

### Limited independent scaling

If chatbot requests become expensive or slow, it is not possible to scale only the chatbot module independently without additional infrastructure.

### Boundaries can weaken over time

Developers may take shortcuts such as:

```text
Calendar code directly reading Favorites tables
Search code directly modifying Recipe tables
```

Over time, this creates strong coupling and makes future changes difficult.

### Shared database can become tightly coupled

Even if the code is modular, direct cross-module database queries can make the modules dependent on one another’s table structures.

### One release affects everything

A small change to the calendar module may require deploying the entire application.

### External services still create distributed-system problems

Although RecipeCove itself is a monolith, Google and the chatbot provider are external systems. Their timeouts, failures, rate limits, and changed APIs still need to be handled.

## 6. Implementation challenges

### Enforcing module boundaries

The team must decide which module owns each rule and each piece of data.

For example:

- The Recipe module should decide whether a recipe exists.
- The Favorites module should decide whether a recipe is already favorited.
- The Calendar module should decide whether an event is valid.
- The Identity module should decide whether a user is authenticated.

This ownership needs to be reflected in code structure and tests.

### Google login

Google login normally involves a redirect-based OAuth or OpenID Connect flow:

1. The user selects “Continue with Google.”
2. RecipeCove redirects the browser to Google.
3. The user authenticates with Google.
4. Google redirects back to a RecipeCove callback URL.
5. RecipeCove verifies the response.
6. RecipeCove finds or creates the corresponding local user.
7. RecipeCove creates a secure local session.
8. The user is redirected into the application.

Important implementation concerns include:

- Protecting the OAuth flow against request forgery.
- Validating the `state` value.
- Validating identity tokens correctly.
- Protecting client secrets.
- Deciding which Google identity value identifies a user.
- Handling an existing local account with the same email address.
- Handling revoked access or changed account information.
- Securely expiring and invalidating sessions.
- Handling Google outages or callback failures.

The application should isolate Google-specific code behind an authentication adapter. This prevents Google API details from spreading throughout the application.

### Chatbot integration

The chatbot is likely more difficult than a normal database feature.

Potential challenges include:

- Choosing an AI provider.
- Defining the supported diet types.
- Ensuring recommendations use valid RecipeCove recipes.
- Preventing unsupported medical or nutritional claims.
- Handling prompt injection or malicious user input.
- Validating the AI response.
- Managing timeouts and provider failures.
- Limiting request frequency and cost.
- Protecting personal information from being sent unnecessarily.
- Providing a fallback when the chatbot is unavailable.

A safer initial design would be for the chatbot to recommend recipes from the RecipeCove catalog rather than freely inventing recipes. The Chatbot module could:

1. Interpret the user’s diet request.
2. Find matching recipes.
3. Send only suitable recipe information to the AI service.
4. Ask the AI service to rank or explain the options.
5. Validate that returned recipe identifiers actually exist.
6. Display the results to the user.

This is more controlled than displaying arbitrary generated recipe data.

### Transaction consistency

Adding a favorite is straightforward, but operations involving multiple modules need clear behavior.

For example, if the user requests “favorite this recipe and add it to my calendar,” the system must decide whether:

- Both actions must succeed together.
- They are two independent actions.
- Partial success is acceptable.
- The user should be allowed to retry only the failed action.

This should not be left unclear in the implementation.

### Testing

The system would need:

- Unit tests for each module’s business rules.
- Integration tests for database operations.
- Authentication flow tests.
- External-service adapter tests.
- End-to-end tests for important user journeys.
- Failure tests for chatbot and Google outages.

Yes, it **could** happen, but it is not automatic.

## How chatbot traffic could affect other users

In a simple modular monolith, chatbot requests might use the same:

- Web-server processes.
- CPU and memory.
- Request threads.
- Database connection pool.
- Network connections.
- Application-wide rate limits.

For example, suppose many users submit chatbot requests at the same time and each request waits 20 seconds for an external AI provider. If the application keeps too many requests open, it could:

1. Use up available request-handling capacity.
2. Consume too much memory.
3. Exhaust database connections.
4. Make ordinary recipe searches wait.
5. Delay calendar operations.
6. Make the whole application appear slow.

The problem is therefore not simply that the chatbot is “inside a monolith.” The main problem is **uncontrolled resource sharing**.

A well-designed modular monolith can isolate expensive work.

## Preventing chatbot problems without adopting microservices

### 1. Use strict timeouts

Every request to the chatbot provider should have a maximum duration.

For example:

```text
Maximum chatbot provider wait: 10 seconds
```

If the provider does not respond within that time, RecipeCove should stop waiting and show a useful fallback message.

Without a timeout, requests could remain open indefinitely.

### 2. Limit concurrent chatbot requests

RecipeCove could allow only a fixed number of chatbot requests to run at once.

For example:

```text
Maximum active chatbot requests: 20
```

Additional requests could be:

- Placed in a queue.
- Rejected temporarily with a retry message.
- Served by a simpler fallback search.

This prevents chatbot traffic from consuming all application capacity.

### 3. Add rate limits and user quotas

The system could limit requests:

- Per user.
- Per IP address.
- Per time period.
- Based on account type.

For example:

```text
A user may make 10 chatbot requests per minute.
```

This protects against accidental overload, abuse, and unexpectedly high AI costs.

### 4. Use a circuit breaker

A circuit breaker temporarily stops calls to the chatbot provider when repeated failures occur.

The behavior could be:

1. Try the chatbot provider normally.
2. Detect repeated failures or timeouts.
3. Stop sending new requests for a short period.
4. Return a fallback response immediately.
5. Try the provider again later.

This prevents RecipeCove from repeatedly waiting for a provider that is already unavailable.

### 5. Use bulkhead isolation

A bulkhead prevents one feature from using all shared resources.

For example, RecipeCove could use separate limits for:

```text
Recipe search: protected request capacity
Calendar operations: protected request capacity
Chatbot: limited request capacity
```

The chatbot would be allowed to use only its allocated capacity. Search and calendar requests would retain their own capacity.

This is similar to compartments in a ship: damage in one compartment does not automatically sink the entire ship.

### 6. Move chatbot work to background workers

Instead of keeping a web request open while waiting for the AI provider, RecipeCove could:

1. Accept the chatbot request.
2. Put it in a queue.
3. Process it using a worker.
4. Store the result.
5. Let the user check for the result or receive an update.

The worker can have a strict limit on the amount of chatbot work it performs.

This can still be part of a modular-monolith solution. The system can use:

- One codebase.
- The same modules.
- One main deployment process.
- A separate worker process for resource isolation.

That is different from immediately splitting the application into independent microservices.

A simple arrangement might be:

```text
Web application process
    ├── Search
    ├── Accounts
    ├── Favorites
    └── Calendar

Chatbot worker process
    └── Chatbot module
```

The chatbot worker could still use the same RecipeCove database and codebase, but it would not consume all web-request capacity.

### 7. Provide a fallback

If the chatbot is unavailable, RecipeCove could still offer ordinary diet filtering:

```text
Show recipes tagged as vegetarian and gluten-free.
```

This is less flexible than an AI chatbot, but it keeps the core recipe-discovery feature available.

### 8. Cache common requests

If many users ask similar questions, the system could cache results for common diet requests.

For example:

```text
“Vegetarian dinner recipes”
```

could be cached for a short period.

Caching reduces:

- AI-provider calls.
- Response time.
- Cost.
- Load on the application.

The cache must be used carefully because recommendations may become outdated.

### 9. Monitor resource usage

RecipeCove should measure:

- Chatbot request count.
- Chatbot response time.
- Timeout rate.
- Provider error rate.
- Queue length.
- CPU and memory usage.
- Database connection usage.
- Recipe-search response time.
- Calendar-operation response time.

This allows the team to determine whether chatbot traffic is actually affecting other features.

## Would this still be a modular monolith?

Yes, these measures do not require an immediate migration to microservices.

A modular monolith can include:

- A normal web application process.
- A background worker process.
- A queue.
- A shared database.
- Clearly separated internal modules.

The code can remain one application codebase, while expensive work is given separate runtime limits.

The distinction is:

### Modular monolith

- Usually one codebase.
- Strong internal modules.
- Often one deployment unit, although workers may run separately.
- Simple internal communication.
- Shared operational environment.

### Microservices

- Independently deployable services.
- Separate service ownership and lifecycle.
- Network communication between services.
- More operational complexity.
- Often separate data ownership and infrastructure.

For RecipeCove, isolating chatbot work in a worker would be a gradual scaling measure, not necessarily a full microservices architecture.

## Could one database become a problem?

Yes, a single database could eventually become a bottleneck, but it is not automatically a problem just because RecipeCove gains users.

A relational database can support a large amount of traffic if:

- Queries are efficient.
- Important columns are indexed.
- Connections are managed.
- Data is modeled correctly.
- Read and write workloads are controlled.
- The database server is sized appropriately.

The important question is not:

> “Does the system use one database?”

It is:

> “What workload must the database support, and how efficiently does it support it?”

## How the database could become a bottleneck

### CPU and disk usage

Large recipe searches, reporting queries, or many simultaneous operations could use too much database CPU or disk I/O.

### Too many connections

If every web request opens a separate database connection, a large number of users could exhaust the database’s connection capacity.

Connection pools and limits are important.

### Lock contention

Many simultaneous writes to the same data can cause transactions to wait.

This is more likely if operations are long or if tables are poorly indexed.

### Slow searches

Searching recipe names with inefficient queries can become slow as the recipe collection grows.

### Storage growth

User calendars, events, favorites, logs, and recipe data will grow over time.

The system needs a storage and cleanup strategy.

### Backup and recovery time

A large database may take longer to back up and restore.

### Availability risk

If the database is a single server with no redundancy, a database failure can affect every module.

## Ways to scale one database

### Use proper indexes

Likely indexes could include:

```text
recipes.name
favorites.user_id
favorites.recipe_id
calendar_events.calendar_id
calendar_events.date
```

The exact indexes should be based on actual query patterns.

### Use pagination

Search and favorites should not load thousands of records in one request.

### Optimize queries

The application should avoid:

- Loading unnecessary columns.
- Repeating the same query many times.
- Unbounded result sets.
- Queries without appropriate filters.

### Use connection pools

A bounded pool prevents the application from opening unlimited database connections.

Separate or reserved capacity can help protect important operations such as login, search, and calendar updates.

### Cache read-heavy data

Recipe and ingredient information may be suitable for caching because it is likely read more often than it changes.

### Add read replicas later

If recipe browsing creates a heavy read workload, read-only queries could be sent to a database replica.

Writes would still go to the main database.

This adds replication complexity, so it should be introduced only when monitoring shows it is necessary.

### Use a specialized search index later

If recipe search becomes complex or the recipe collection becomes very large, a search engine could handle search separately.

The Recipe Catalog would remain the source of truth, while the search index would optimize discovery.

### Improve database availability

A production system might use:

- Automated backups.
- Point-in-time recovery.
- Database replication.
- Failover.
- Monitoring.
- Restore testing.

These improve reliability without requiring separate databases for every module.

## When separate databases might be justified

Separating databases becomes more reasonable if:

- The database is proven to be a performance bottleneck.
- A module has a very different scaling pattern.
- Search needs a specialized storage system.
- The chatbot needs independent data-processing storage.
- Independent ownership or deployment is required.
- Database failures in one area must not affect another.
- The team has the operational capacity to manage the additional systems.

It should be based on measured requirements, not only on the possibility of future growth.

## Main trade-off

The practical progression could be:

```text
One modular application
    ↓
Add timeouts, rate limits, caching, and monitoring
    ↓
Move chatbot work to a bounded worker
    ↓
Optimize and protect the shared database
    ↓
Add replicas or a search index if measurements justify them
    ↓
Extract a separate service only if independent scaling is truly needed
```

This avoids premature microservices while still providing a path for growth.

## Conclusion

Many simultaneous chatbot users **could** affect recipe search or calendars if chatbot requests are allowed to consume unlimited shared resources.

However, this can be controlled within a modular-monolith approach using:

- Timeouts.
- Concurrency limits.
- Rate limits.
- Circuit breakers.
- Bulkhead isolation.
- Background workers.
- Caching.
- Fallback search.
- Monitoring and load testing.

One database can also support substantial growth if it is properly designed and monitored. It may eventually need optimization, replicas, or a specialized search index, but immediately splitting it into several databases would introduce additional complexity.

The important architectural principle is:

> Start with simple shared infrastructure, but enforce resource boundaries so that expensive or unreliable features cannot overwhelm essential features.

## 5. Disadvantages compared with a modular monolith

### More operational complexity

Instead of deploying one application, the team must manage:

- Multiple applications.
- Multiple deployments.
- Service discovery or routing.
- Configuration for each service.
- Network policies.
- Logs from multiple services.
- Monitoring and alerting.
- Possibly multiple databases.
- Message brokers and queues.

### Network failures

An in-process method call is usually simple. A service-to-service call can fail because of:

- Network problems.
- Timeouts.
- DNS or routing problems.
- Service overload.
- Authentication errors.
- Version incompatibilities.

### Higher latency

A request such as “show my favorite recipes” might require calls to multiple services:

```text
Web application
    → Favorites Service
        → Recipe Catalog Service
```

Each network call adds latency.

### Distributed data consistency

In a modular monolith, adding a favorite and creating related data might be handled by one database transaction.

In microservices, those operations may use different databases. A single transaction cannot normally cover both databases easily.

The system must handle partial success.

### More difficult debugging

A single user request might pass through:

```text
Gateway
    → Identity Service
    → Favorites Service
    → Recipe Catalog Service
    → Favorites database
```

When something fails, developers need correlated logs and distributed tracing to understand the complete request path.

### More difficult local development

To run the entire system locally, a developer may need to start:

- Several services.
- Several databases.
- A message broker.
- A search engine.
- An AI integration mock.

This is much heavier than starting one modular application.

### Higher cost

Multiple running services and databases generally require more infrastructure and more maintenance.

### Duplicated data

The Search Service and Recommendation Service may each need a copy of recipe data.

Copies must be updated correctly, which introduces synchronization problems.

## 8. Failure-handling techniques

Microservices require several reliability mechanisms.

### Timeouts

A service should not wait forever for another service.

### Limited retries

Retries can help with temporary failures, but unlimited retries can make overload worse.

### Circuit breakers

A circuit breaker temporarily stops calls to a failing service and returns a controlled response.

A serious problem can occur if the system:

2. Crashes before publishing `FavoriteAdded`.

2. Sends events to the broker.

## The “exactly once” problem

A reminder system usually cannot guarantee true **exactly-once delivery** in every situation.

For example, the notification provider may receive the reminder successfully, but RecipeCove may lose the response because of a network failure. RecipeCove then cannot know whether it should retry:

```text
RecipeCove sends reminder
    → provider receives it
    → response is lost
    → RecipeCove retries
```

The retry could create a duplicate notification.

A more realistic goal is:

> Process each reminder safely and make duplicate user-visible reminders extremely unlikely.

This is often called **effectively-once delivery**.

## How to avoid losing reminders

The calendar operation should store the reminder durably in the database.

For example:

```text
reminder_id: 987
calendar_event_id: 456
user_id: 42
scheduled_time: ...
status: pending
```

The reminder should not exist only in memory or only inside a temporary message.

A background scheduler can periodically find reminders whose time has arrived:

```text
Find pending reminders due now
    → process them
```

If the application restarts, the reminder remains in the database and can still be found.

### Transactional outbox

If RecipeCove uses an event broker, the calendar operation could save:

1. The calendar event.
2. An outbox record saying that a reminder must be scheduled.

Both records should be saved in the same database transaction.

If the application crashes after saving, a background publisher can later send the outbox message. This prevents the event from being lost between the calendar update and event publication.

## How to avoid processing a reminder twice

Every reminder should have a stable unique identifier, such as:

```text
reminder_id = 987
```

The reminder processor should store its processing status:

```text
pending
processing
sent
failed
```

It should also have a uniqueness rule such as:

```text
Only one delivery record may exist for reminder_id 987
```

If the same event is received twice, the consumer checks the delivery record:

```text
Reminder 987 has already been sent
    → do not send it again
```

This is called **idempotent processing**.

The consumer should acknowledge the message only after it has safely recorded the result. If it crashes before acknowledgement, the message may be delivered again, but the unique reminder ID prevents normal duplicate processing.

## Important limitation with external notification providers

Idempotency works best if the email, push-notification, or messaging provider also supports an idempotency key:

```text
provider_request_id: reminder-987
```

Then, if RecipeCove sends the same request twice, the provider recognizes it as the same operation and does not send two notifications.

If the provider does not support idempotency, there is an unavoidable small risk:

```text
Provider sends notification
    → RecipeCove does not receive confirmation
    → RecipeCove retries
```

In that situation, RecipeCove cannot know with certainty whether the first notification was delivered.

For that reason, a system should not promise absolute exactly-once delivery unless the complete notification path supports it.

## Handling different failure cases

### Case 1: Event is lost before processing

Solution:

- Store the reminder in the database.
- Use an outbox or a scheduler.
- Retry unsent reminders.
- Monitor pending reminders.

### Case 2: Event is delivered twice

Solution:

- Use a stable `reminder_id`.
- Store a delivery record.
- Enforce uniqueness.
- Make the consumer idempotent.

### Case 3: Sending fails clearly

For example, the provider returns an error.

Solution:

- Keep the reminder as `failed` or `pending`.
- Retry according to a limited retry policy.
- Record the error.
- Alert administrators after repeated failures.

### Case 4: The result is unknown

For example, the network connection fails after the provider may have accepted the reminder.

Solution:

- Use the provider’s idempotency key if available.
- Retry using the same key.
- Do not create a new logical reminder.
- Mark the attempt as uncertain until the provider confirms the result.

### Case 5: The user deletes the calendar event

The reminder should be cancelled or marked inactive. A worker must check that the reminder is still valid before sending it.

## Simple implementation for RecipeCove

For a small RecipeCove project, I would avoid starting with a full message broker and distributed event system.

A simpler design would be:

```text
Calendar module
    → saves calendar event and reminder in the database

Background scheduler
    → finds due pending reminders
    → safely claims one reminder
    → sends the notification
    → marks it as sent
```

A simplified process would be:

1. Query for due reminders with status `pending`.
2. Atomically change one reminder to `processing`.
3. Send the notification using its stable reminder ID.
4. If successful, change status to `sent`.
5. If it fails, change status back to `pending` or `failed`.
6. Retry later according to a limit.

The “claim” operation must be atomic so that two scheduler instances do not process the same reminder at the same time.

For example:

```text
Only claim reminder 987 if its current status is pending.
```

If another worker has already changed it to `processing`, the second worker skips it.

## Is this too complicated for a small project?

A full event-driven implementation could be too complicated for RecipeCove at this stage.

It might require:

- A message broker.
- An outbox.
- Consumer processes.
- Retry queues.
- Dead-letter queues.
- Duplicate detection.
- Event monitoring.
- Distributed tracing.
- Provider-specific idempotency.

That is a lot of infrastructure for a feature whose exact reminder requirements are not yet defined.

### Proportional solution

For the current project, a reasonable design would be:

- One relational database.
- Calendar events and reminders stored together.
- One background scheduler or worker.
- Reminder status and retry information.
- Stable reminder identifiers.
- A simple unique constraint.
- Clear error logging.
- In-app reminders first, if external notifications are not required.

This gives useful reliability without introducing a full distributed architecture.

## Recommended progression

RecipeCove could evolve gradually:

```text
Initial version:
    Database reminder records
    Background scheduler
    Status tracking
    Basic retries

If usage grows:
    Separate worker process
    Queue for reminder jobs
    Better monitoring

If scale becomes significant:
    Transactional outbox
    Dedicated notification service
    Provider idempotency
    Dead-letter processing
```

## Conclusion

The system cannot always guarantee mathematical exactly-once delivery when external services are involved. It should instead aim for **effectively-once reminders** by using:

- Durable reminder records.
- Stable reminder IDs.
- Atomic claiming.
- Idempotent processing.
- Unique delivery records.
- Limited retries.
- Provider idempotency keys when available.
- Reconciliation and monitoring.

For RecipeCove, a database-backed scheduler is probably the right starting point. A full event-driven reminder platform would likely be disproportionate to the current project size.

# Recommended choice: Modular Monolith

RecipeCove

# Main advantages of the modular monolith

The team can work with one application, one main deployment, and one database.

## Easier transactions

- The whole application cannot scale as selectively as microservices.

- Boundaries must be actively protected in the code.

Microservices would provide genuine benefits:

- Independent deployment.
- Independent scaling.
- Stronger resource isolation.
- Separate database ownership.
- More flexibility for large teams.

They could be useful if the chatbot became extremely busy or if RecipeCove grew substantially.

- Network failures and latency.
- Distributed authentication.
- Multiple deployments.
- More complex local development.
- API versioning.
- Distributed tracing.
- Separate database management.
- Eventual consistency.
- Cross-service workflow failures.
- Duplicate requests and idempotency.
- More expensive monitoring and operations.

For example, if Favorites succeeds but Calendar fails, the system must manage partial success, retries, duplicate prevention, and possibly compensation. A modular monolith can often handle related operations using a single database transaction.

Microservices would therefore be a reasonable future evolution, but they appear disproportionate to the current RecipeCove requirements.

# Why a fully event-driven architecture is less suitable as the default

Event-driven design is valuable for work that does not need to finish immediately, such as:

- Sending calendar reminders.
- Updating recommendations.
- Recording analytics.
- Updating a search index.
- Processing chatbot requests.
- Sending notifications.

However, using events for every operation would make the system harder to understand.

Challenges include:

- Eventual consistency.
- Lost messages.
- Duplicate messages.
- Out-of-order messages.
- Retry policies.
- Dead-letter queues.
- Event schema versioning.
- Harder debugging.
- More complex testing.
- Additional broker infrastructure.

For example, after a user schedules a recipe, a reminder event might be processed twice. The system would need stable reminder IDs, idempotent consumers, durable status records, and safe retries.

For a small project, a database-backed scheduler or bounded background worker is probably sufficient. A full event broker can be added later if usage justifies it.

# Main implementation challenges for the recommended architecture

## 1. Enforcing module boundaries

Each module should own its business rules and tables.

For example:

- Identity owns authentication and user identity.
- Recipe Catalog owns recipe and ingredient data.
- Favorites owns favorite relationships.
- Calendar owns calendars and events.
- Chatbot owns provider interaction and recommendation logic.

Modules should use public interfaces rather than directly modifying one another’s tables.

## 2. Google authentication

The Google integration must correctly handle:

- OAuth or OpenID Connect redirects.
- `state` validation.
- Token validation.
- Secure client-secret storage.
- Account linking.
- Session creation and expiration.
- Login failures.
- Revoked or changed Google accounts.

Google-specific code should be isolated behind an authentication adapter.

## 3. Chatbot reliability and safety

The chatbot needs:

- Strict provider timeouts.
- Rate limits.
- Concurrency limits.
- Cost controls.
- Retry limits.
- Circuit breakers.
- Output validation.
- A fallback to ordinary diet-based recipe search.
- Protection against unsafe or unsupported recommendations.

A separate worker process can isolate chatbot load while keeping the overall codebase modular.

## 4. Database performance

The database should use:

- Appropriate indexes.
- Pagination.
- Efficient queries.
- Bounded connection pools.
- Caching for read-heavy recipe data.
- Backups and recovery procedures.
- Monitoring for slow queries and resource usage.

If the system later grows significantly, read replicas or a separate search index can be considered.

## 5. Reliable favorites, calendar events, and reminders

Favorites should have a uniqueness rule such as:

```text
Unique(user_id, recipe_id)
```

Reminder processing should use:

- Stable reminder identifiers.
- Durable database records.
- Atomic claiming.
- Status tracking.
- Limited retries.
- Idempotent processing.

True exactly-once notification delivery cannot always be guaranteed when external providers are involved, but effectively-once delivery can be approached carefully.

# Final architectural recommendation

Use this progression:

```text
Initial architecture:
    Modular monolith
    + one relational database
    + strict module boundaries
    + background worker for chatbot and reminders

As usage grows:
    Add caching, queues, and stronger monitoring
    Add a separate chatbot worker if needed
    Add a search index or read replica if measurements justify it

Only later, if necessary:
    Extract Chatbot, Search, or another module into a microservice
```

The central decision is:

> Start with a modular monolith because it is the simplest reliable architecture for the current RecipeCove scope, while using selective event-driven and worker-based techniques to isolate expensive or asynchronous work.
